# Single host service owns shared conference data

## Status

Accepted

One local Veto Host Service is the authoritative source for shared Conference data, authentication, authorization, command handling, and LAN routing on one computer. Its dependency-free Host Runtime owns ordinary TypeScript domain state and exposes one authoritative `execute(actor, command)` mutation path for Host Console and UserClient writes that change shared data. Each UserClient command includes a durable idempotency key so a lost acknowledgement cannot create duplicate content. The first release exposes one active Conference, selected by an explicit Host Console action; after a Host restart no Conference is active until explicitly started again. The service isolates every query, command, connection, and event by its Conference and Committee, persists each successful command before acknowledging it, and restores UserClients from a fresh snapshot after a restart. Switching the active Conference disconnects UserClients, returns them to their home screen, and requires each affected Chair to put its bound Display into a disconnected state. Security-relevant Host Console changes to a Seat revoke its active session immediately. The local-only Host Console is an administrative interface, not a Chair control surface. Seat-authenticated UserClients remain the primary source of directives, news, and situation updates; they pull Host-owned state, may retain disconnected LocalDrafts, and never queue state-changing commands. A normal UserClient receives only its own identity, Committee, resolved Capabilities, and authorized content; it never receives other seats, procedural state, agenda, Battle, Participants, User data, or invite codes.

A Chair is a UserClient whose authenticated Seat has both `control_conference` and one explicit ChairAssignment. It actively obtains only that ChairCommitteeProjection from Host Service, then owns the local agenda and ProcedureSeatState for that Committee. This local overlay may mark attendance, voting rights, and procedure order, but never changes Host-owned Seat identity, role, Capability, User binding, or Committee membership. It persists only on the Chair's device and has no first-release cross-device migration or takeover path. A Display is bound directly to its Chair, not to Host Service; Host's authorization and audit boundary ends when it sends the Chair projection. Chair-to-Display communication is a trusted presentation link operated by the Chair. Business content is created and published only by Seat-authenticated UserClients, including Chairs acting as their own Seat; Host Console never acts as a content source and may only perform security or recovery actions. Every content item records its source Seat and Committee. There is no individual-Seat routing or free-form recipient list: published news and situation updates are always broadcast to the whole Conference, while a directive has exactly one target Committee. Review and processing queues remain restricted workflow audiences, not general content listings. Published news and situation updates are immutable: an authorized Seat may withdraw them with a recorded reason, which removes them from normal listings while preserving the audit history, and corrections are new items. Directives are atomically claimed by one eligible processor before entering `processing`; their sender may cancel an unclaimed submission, and an exceptional Host Console release is audited. Files remain outside the first implementation scope and do not yet have a routing rule.
